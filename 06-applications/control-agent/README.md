# 합정 현장 에이전트 — 설치 가이드

조명(Tasmota)을 원격 제어하려면 **합정에 상주하는 맥 한 대**가 필요하다. 이 문서는 그 맥에서
처음부터 끝까지 밟는 절차다. 위에서 아래로 순서대로 하면 된다.

```
Tasmota ──평문 1883──> RPi mosquitto ──rpi-bridge(tailscale)──> 맥 mosquitto ──> [에이전트]
         (LAN)              ↑                                     (이 맥)          │
                            │                                        │             │ HTTPS/WSS
                            └── AWS IoT Core ←── aws-iot-cmnd-bridge─┘  Supabase <─┘ (아웃바운드만)
                                (Pi 자체 브릿지)                            └──> admin.html
```

기기가 붙는 브로커는 **RPi**고, 이 맥의 브로커는 그걸 브릿지로 받아온다.

**명령이 기기까지 가는 길은 둘이다.** 맥 브로커가 같은 `cmnd/#`를 rpi-bridge(tailscale)와
AWS IoT Core로 **항상 병렬로** 내보내고, RPi는 자체 AWS 브릿지로 후자를 직접 구독한다.
둘 중 하나가 죽어도 명령이 산다.

**인바운드 포트를 열지 않는다.** 두 방향 다 이 맥이 나가서 맺는 연결이라, 공유기 포트포워딩·
DDNS·터널이 전부 불필요하다.

> **왜 맥이 필요한가**: Tasmota 기기가 LAN 평문 MQTT로만 붙게 돼 있다(ESP8266은 TLS가 버겁다).
> 그래서 같은 LAN 안에 브로커가 있어야 한다. 냉난방(ThinQ)은 이것과 무관하게 클라우드 API라
> 맥이 꺼져 있어도 동작한다 — **조명만 이 맥에 의존한다.**

## 설치 절차

**→ [`../control-setup.md`](../control-setup.md) 의 B 단계를 따른다.**

절차를 그쪽 한 군데에만 둔 이유: 냉난방과 조명 절차를 따로 두면 현장에서 두 문서를 번갈아 보게 되고,
한쪽만 고쳐지면 조용히 어긋난다. 이 문서는 **왜 그렇게 동작하는지**만 다룬다.

## 문제 해결

| 증상 | 확인 |
|---|---|
| `[realtime] SUBSCRIBED`가 안 뜬다 | service_role 키, 인터넷. 이게 없으면 명령이 안 온다 |
| 조명 카드가 "아직 상태를 받은 적 없음" | 기기가 브로커에 못 붙은 것. Tasmota Console에서 `MqttHost`·`MqttUser` 확인 |
| 명령을 눌러도 반응 없음 | `agent.log`에 `[cmd] 발행`이 있나 → 있으면 기기 쪽, 없으면 Realtime 쪽 |
| `[cmd] 만료 — 실행하지 않음` | 정상이다. 60초 넘은 명령은 일부러 버린다(아래) |
| 기기 IP가 바뀌어 먹통 | 2단계 DHCP 예약이 풀렸는지 확인 |

## 설계상 알아둘 것

- **움직임 감시(`src/motion*.js`)는 이 프로세스가 아니라 카메라 relay `.app` 아래에서 돈다.**
  합칠 수 없는 이유가 권한이다 — macOS 26이 로컬 네트워크 접근을 바이너리 단위로 통제해,
  launchd 직속인 이 에이전트의 Node는 카메라 IP에 `EHOSTUNREACH`가 난다. **같은 코드가
  터미널에서는 200이다**(2026-08-18 실측). 그래서 여기에 넣으면 에러 없이 아무것도 못 보는,
  제일 나쁜 방식으로 죽는다. 그 권한을 이미 통과한 주체가 `TypeLoungeCameraRelay.app`이라
  거기에 얹었다. 절차는 `cctv-setup.md` C-10에 있다.
  > 같은 이유로 **`tasmota-http.js`의 HTTP 우회도 launchd 아래에서는 못 붙을 가능성이 크다**
  > (조명 IP가 카메라와 같은 `192.168.200.x` 대역이다). 브릿지가 살아 있으면 안 도는 경로라
  > 아직 실제로 밟힌 적이 없어 확인되지 않았다 — 조명이 '먹통인데 이유를 모르겠다'가 되면
  > 여기부터 의심한다.
- **오래된 명령은 실행하지 않는다.** 맥이 꺼져 있던 동안 쌓인 명령을 재생하면 새벽 3시에 조명이
  켜진다. 60초(`config.js`의 `COMMAND_TTL_MS`)가 지난 명령은 `expired`로 버린다.
- **`sent`는 '기기가 답했다'는 뜻이다.** 예전에는 로컬 브로커에 발행만 하면 `sent`였다. 로컬
  브로커는 맥이 켜져 있는 한 항상 성공하므로 그 기록은 아무것도 말해주지 않았고, 정작 기기까지
  가는 rpi-bridge 구간은 `cmnd/# out`이 QoS 0이라 브릿지가 죽어 있으면 메시지가 조용히
  사라졌다 — 조명은 그대로인데 화면은 '보냄'. `pending`으로 남지 않으니 재시도도 안 걸렸다.
  지금은 발행 뒤 기기의 `stat` 보고를 4초(`config.js`의 `CONFIRM_TIMEOUT_MS`) 기다려 확인한다.
- **명령은 한 번 발행하고, 퍼뜨리는 건 브로커가 한다.** 에이전트는 로컬 브로커에 `cmnd`를
  한 번 던질 뿐이고, mosquitto가 그걸 rpi-bridge와 aws-iot-cmnd-bridge 양쪽으로 내보낸다.
  경로를 조건부로 고르지 않는 이유는 **mosquitto에 그런 표현이 없기 때문**이다 — 브릿지
  방향은 정적이라 "tailscale 먼저, 안 되면 AWS"를 이 계층에서 만들 수 없다. 그래도 되는
  이유는 우리가 보내는 명령이 전부 멱등(`POWER ON`/`POWER OFF`)이라, 같은 값이 두 번 닿아도
  결과가 같아서다.
- **MQTT가 막히면 기기 HTTP로 우회한다.** 로컬 브로커부터 없으면(Tier 1) 기다릴 것도 없이
  바로, 발행은 됐는데 4초 안에 기기가 답을 안 하면(Tier 2) 그때 우회한다. 기기가
  맥과 같은 LAN에 있고 `Webserver 2`/`HTTP_API 1`이 켜져 있어 가능하다. IP는 재접속마다
  보내는 `Status 5`의 응답에서 얻는다 — DHCP라 미리 아는 값이 아니고, 스캔은 못 쓴다
  (254개 병렬 요청에 ESP8266이 실제로 응답을 놓쳤다).
- **'브릿지가 끊겼으면 바로 HTTP'라는 단계가 있었는데 없앴다.** rpi-bridge의 `cmnd/# out`이
  QoS 0이라 그 브릿지가 죽으면 유실이 확정이었고, 확정된 유실을 4초 기다리는 건 낭비였다.
  AWS 병렬 경로가 생기면서 그 전제가 깨졌다 — 브릿지가 죽어도 명령은 tailscale과 무관하게
  기기까지 갈 수 있으므로, 그때 HTTP로 직행하면 **AWS로 나간 사본이 도착할 기회를 뺏고**
  병렬 경로를 만든 이유를 스스로 없앤다. 브릿지 생사는 **명령 배달 판정에는 쓰지 않는다** —
  상태 전이 로그와, stat이 못 오는 동안 상태를 HTTP로 대신 읽는 재동기화 판정
  (`bridge-health.js`)에만 쓴다. 그 판정은 '끊김 확정'뿐 아니라 브로커가 안 붙어 생사를
  모르는 상태도 60초 유예 뒤 재동기화로 넘긴다 — 그동안도 stat은 안 오기 때문이다.
- **두 브릿지가 같은 접두사를 반대 방향으로 실으면 무한 루프가 된다.** mosquitto는 "들어온
  브릿지로 되돌려 보내지 않기"만 하고 다른 브릿지로 나가는 건 막지 않는다. 그래서
  `mosquitto.conf`는 `tele`/`stat`은 aws-iot-bridge만 `out`, `cmnd`는 aws-iot-cmnd-bridge만
  `out`으로 갈라 둔다. 토픽을 추가할 때 이 불변식을 먼저 확인한다 — AWS IoT는 건당 과금이라
  루프가 조용히 비싸다.
- **`power = null`('모름')은 `'OFF'`가 아니다.** 연결이 끊겨도 마지막 전원값은 유지된다 —
  `LWT=Offline`은 `online`만 바꾸고 `power`는 건드리지 않는다. 이 둘을 합치면 꺼진 줄 알았는데
  켜져 있는 상황이 조용히 숨는다.
- **mosquitto 설정은 인증이 기본으로 켜져 있다.** Space는 레포 템플릿이 `allow_anonymous true`였고
  실제 하드닝은 사람이 SSH로 한 것이라, "재설치하면 permissive 기본값이 되살아난다"는 갭이
  남아 있었다. 여기서는 안전한 값이 레포에 있어 설치하면 그대로 적용된다.
