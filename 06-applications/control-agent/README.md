# 합정 현장 에이전트 — 설치 가이드

조명(Tasmota)을 원격 제어하려면 **합정에 상주하는 맥 한 대**가 필요하다. 이 문서는 그 맥에서
처음부터 끝까지 밟는 절차다. 위에서 아래로 순서대로 하면 된다.

```
Tasmota ──평문 1883──> mosquitto ──> [에이전트] ──HTTPS/WSS──> Supabase ──> admin.html
         (LAN)          (이 맥)                    (아웃바운드만)
```

**인바운드 포트를 열지 않는다.** 두 방향 다 이 맥이 나가서 맺는 연결이라, 공유기 포트포워딩·
DDNS·터널이 전부 불필요하다.

> **왜 맥이 필요한가**: Tasmota 기기가 LAN 평문 MQTT로만 붙게 돼 있다(ESP8266은 TLS가 버겁다).
> 그래서 같은 LAN 안에 브로커가 있어야 한다. 냉난방(ThinQ)은 이것과 무관하게 클라우드 API라
> 맥이 꺼져 있어도 동작한다 — **조명만 이 맥에 의존한다.**

---

## 설치 절차

**→ [`../control-setup.md`](../control-setup.md) 의 B 단계를 따른다.**

절차를 그쪽 한 군데에만 둔 이유: 냉난방과 조명 절차를 따로 두면 현장에서 두 문서를 번갈아 보게 되고,
한쪽만 고쳐지면 조용히 어긋난다. 이 문서는 **왜 그렇게 동작하는지**만 다룬다.

## 문제 해결

| 증상 | 확인 |
|---|---|
| `[realtime] SUBSCRIBED`가 안 뜬다 | service_role 키, 인터넷. 이게 없으면 명령이 안 온다 |
| 조명 카드가 "아직 상태를 받은 적 없음" | 기기가 브로커에 못 붙은 것. Tasmota Console에서 `MqttHost`·`MqttUser` 확인 |
| 명령을 눌러도 반응 없음 | `agent.log`에 `[cmd] 발행`이 있나 → 있으면 기기 쪽, 없으면 Realtime 쪽 |
| `[cmd] 만료 — 실행하지 않음` | 정상이다. 60초 넘은 명령은 일부러 버린다(아래) |
| 기기 IP가 바뀌어 먹통 | 2단계 DHCP 예약이 풀렸는지 확인 |

## 설계상 알아둘 것

- **오래된 명령은 실행하지 않는다.** 맥이 꺼져 있던 동안 쌓인 명령을 재생하면 새벽 3시에 조명이
  켜진다. 60초(`config.js`의 `COMMAND_TTL_MS`)가 지난 명령은 `expired`로 버린다.
- **응답의 `sent`는 '기기가 실행했다'가 아니다.** 브로커에 발행했다는 뜻이다. 실제 반영은 기기가
  `stat` 토픽으로 보고하고, 그걸 에이전트가 `device_state`에 쓴다.
- **`power = null`('모름')은 `'OFF'`가 아니다.** 연결이 끊겨도 마지막 전원값은 유지된다 —
  `LWT=Offline`은 `online`만 바꾸고 `power`는 건드리지 않는다. 이 둘을 합치면 꺼진 줄 알았는데
  켜져 있는 상황이 조용히 숨는다.
- **mosquitto 설정은 인증이 기본으로 켜져 있다.** Space는 레포 템플릿이 `allow_anonymous true`였고
  실제 하드닝은 사람이 SSH로 한 것이라, "재설치하면 permissive 기본값이 되살아난다"는 갭이
  남아 있었다. 여기서는 안전한 값이 레포에 있어 설치하면 그대로 적용된다.
