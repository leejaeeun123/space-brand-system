# SpaceCloud 자동화

이 폴더는 스페이스클라우드에서 두 가지를 가져온다.

| 무엇 | 어디로 | 문서 |
|---|---|---|
| **예약** (누가 언제 무엇을 빌렸나) | `reservations` | 이 문서 아래 전부 |
| **운영지표** (도달·클릭·예약·후기·키워드) | `sc_daily_stats` · `sc_daily_keywords` | 이 문서 맨 끝 [운영지표 수집](#운영지표-수집) |

둘은 **원천도 목적도 다르다** — 예약은 손님을 받기 위한 장부이고, 지표는 장사가 어떻게 되고
있는지 보는 계기판이다. 다만 파트너 토큰 사정(24시간·재로그인)은 똑같아서 인증 코드는 같은
모양을 공유한다.

# SpaceCloud 예약 자동 반영

`admin.html`이 쓰는 Supabase RPC(`admin_add_reservation` / `admin_set_cancelled`)로 스페이스클라우드
예약을 반영한다. **경로가 둘이다 — API가 주 경로, Gmail이 백업.**

| | 파일 | 역할 |
|---|---|---|
| **주** | `spacecloud-api-sync.js` | 파트너 API에서 직접 수집. 연락처·이메일·인원·사용목적까지 채운다. 수동 실행 |
| **백업** | `spacecloud-gmail-sync.gs` | 알림 메일 파싱. 15분 트리거로 항상 돌아 누락을 막는다 |

두 경로 모두 예약번호(`booking_no`)로 중복을 거르므로 **같이 돌아도 안전하다**
(DB에도 `booking_no` unique index가 있다). 어느 쪽이 먼저 넣든 나중 것은 건너뛴다.

**왜 둘 다 두는가** — API는 데이터가 완전하지만 24시간마다 사람이 재로그인해야 하고 브라우저가 필요하다.
Gmail은 필드가 부실하지만 구글 서버에서 무인으로 항상 돈다. 서로의 구멍을 정확히 메운다.
특히 **취소건은 API가 예약자명을 마스킹**(`윤**`)하고 연락처를 안 주는데, Gmail 취소 메일에는 실명이 온다.

---

## 백업 경로 — Gmail → Supabase

`office@spacecloud.kr`에서 오는 "예약 완료"/"취소 완료" 메일을 감지해 자동 반영하는 Google Apps Script.

## 설치

1. https://script.google.com → 새 프로젝트 생성 (Gmail을 수신하는 계정, 즉 `nmwc.ai@gmail.com`으로 로그인한 상태에서).
2. `spacecloud-gmail-sync.gs` 내용을 통째로 붙여넣기.
3. 좌측 톱니바퀴(프로젝트 설정) → **스크립트 속성** → 속성 추가:
   - 키: `ADMIN_PASSWORD`
   - 값: `admin.html` 로그인에 쓰는 그 관리자 비밀번호
   - ⚠️ **비밀번호를 회전하면 이 값도 같이 바꾼다.** 여기는 비밀번호를 **보관**하는 세 자리 중
     하나다(나머지 둘은 DB `admin_secret`과 Edge Function 시크릿 — `control-setup.md` M절).
     여기만 뒤처지면 **예약 자동 등록만** 죽는데, 어드민도 기기 제어도 문자도 멀쩡해서
     알림이 뜨기 전까지 안 보인다. 2026-08-14에 실제로 그렇게 예약 2건이 반려됐다.
   - 키: `MATTERMOST_WEBHOOK_URL`
   - 값: `https://mm.nmwc.ai.kr/hooks/<웹훅 ID>` (Mattermost 알림용. 아래 "Mattermost 알림" 참고. 비워두면 알림만 조용히 생략되고 예약 처리는 정상 동작)
4. 함수 선택 드롭다운에서 `createTrigger` 선택 후 실행 → Gmail 권한 승인 팝업 승인.
   (15분마다 `processSpaceCloudReservations`, 하루 1회(오전 9시) `dailyAudit`를 도는 트리거가 생성됨)
5. 확인: `processSpaceCloudReservations`를 수동으로 한 번 실행해보고 실행 로그(보기 → 실행 기록)에서 에러가 없는지 확인.

## 동작 방식

> **처리 단위는 스레드가 아니라 메시지다.** 스페이스클라우드는 모든 예약 메일의 제목이 같아서
> Gmail이 한 스레드로 묶는다. 예전엔 스레드에 라벨을 붙이고 `-label:`로 걸렀는데, 라벨이 붙은
> 뒤 같은 스레드로 들어온 메일은 쿼리에서 통째로 사라져 **예약이 조용히 누락**됐다.
> (2026-08-03 예약 스레드는 09:12~14:04 5건이 한 덩어리였다 — 15분 트리거가 그걸 한 번에 담는
> 건 불가능하다. 8/4 마보연 3건이 무사했던 건 우연히 한 15분 창 안에 들어왔기 때문이다.)
> 지금은 처리한 `messageId`를 스크립트 속성 `PROCESSED_MESSAGES`에 남겨 거른다.
> **라벨은 사람이 Gmail에서 훑어보기 위한 표시일 뿐 재처리 여부를 결정하지 않는다** —
> 라벨을 손으로 떼도 다시 처리되지 않고, 재처리하려면 `reprocessMessages()`를 쓴다.

- 검색 쿼리: `from:office@spacecloud.kr subject:("예약 완료" OR "취소 완료") newer_than:7d`
- **도착 시각 오름차순으로 처리한다.** 취소 메일이 그 예약의 등록 메일보다 먼저 처리되면 취소할
  대상을 못 찾아 실패한다(2026-08-03 10:53 "취소 대상 예약을 찾지 못했습니다"가 그 사례다).
  정렬해두면 예약이 항상 먼저 들어간다.
- 스레드 검색 결과 안에 조건과 무관한 메시지가 섞일 수 있어 **발신자와 제목을 메시지 단위로 재확인**한다.
- **예약 완료 메일**: 본문 표(예약공간·예약내용·예약인원·예약옵션·요청사항·예약자명·결제수단·결제금액)를 정규식으로 추출해 `admin_add_reservation` 호출.
  - "MY 예약 상세 페이지" 링크에서 예약번호(예: `10388381`)를 함께 추출해 `p_booking_no`로 저장.
  - **예약번호 추출에 실패하면 조용히 넘어가지 않고 예약자명 실패와 동급으로 에러 처리한다** — 스클이 링크 형식을 바꾸면 `p_booking_no`가 null로 들어가는데, DB unique 인덱스가 partial(`booking_no is not null`)이라 못 막아 API 경로가 같은 예약을 둘째 행으로 또 등록한다. 그래서 재시도(3회)→포기 알림을 태운다.
  - `예약공간`(예: `[오픈특가]TYPE LOUNGE`)은 별도 컬럼이 없어 `p_memo`에 원문 그대로 저장.
- **취소 완료 메일**: 예약번호가 없어 (날짜, 시작/종료 시간)으로 기존 예약을 찾아 `admin_set_cancelled`로 **삭제가 아닌 상태 변경**만 수행 (`cancelled = true`). admin.html에는 "취소됨" 배지로 표시됨.
  - **멱등하다.** 찾은 예약이 이미 `cancelled = true`면 RPC도 알림도 없이 조용히 넘어간다. 같은 취소 메일이 다시 처리되는 상황(라벨 수동 해제, 수동 재실행, 취소 메일이 예약 메일보다 먼저 처리되는 순서 역전)이 실제로 발생했다 — 2026-08-03 10:53 "취소 대상 예약을 찾지 못했습니다" 알림이 그 사례로, 매칭 조건에 `!cancelled`가 들어 있어 **이미 취소된 예약**과 **존재하지 않는 예약**이 구분되지 않던 것이 원인이었다.
  - **재예약 겹침 방어.** 같은 (날짜+시작+종료)에 A=취소·B=활성 두 행이 공존할 수 있다(A가 취소한 슬롯을 B가 재예약). 이때 A의 취소 메일이 재처리되면 이름 대조 없이는 무고한 B를 취소시킨다 — 그래서 **취소 메일의 예약자명으로 대상을 특정**한다. 이미 취소된 후보 중 같은 이름이 있으면 '이미 반영된 취소'로 보고 활성 행을 건드리지 않는다. 대가: 같은 사람이 취소→재예약→다시 취소하면 두 번째 취소가 재처리와 구분되지 않아 조용히 스킵된다(놓친 취소가 무고한 취소보다 안전하다는 선택).
  - 해당 시간대에 예약이 **아예 없을 때만** 에러로 처리한다(예: 자동화 도입 전에 만들어진 예약) — 실패 알림 메일 + Mattermost로 수동 확인 유도.
- **실패는 3번까지 조용히 재시도한다.** 일시적인 RPC 오류는 대개 여기서 낫고, 진짜 문제만 45분 뒤
  한 번 알림이 나간다 — 15분마다 같은 실패를 알리면 알림 자체가 무시된다. 3회를 소진하면 실행 계정
  메일 + Mattermost로 1회 알리고 그 메시지는 포기 상태(`-1`)로 기록한다.
- **포기한 건은 원인을 고쳐도 저절로 안 돌아온다.** 포기 상태(`-1`)는 다음 트리거에서 통째로
  건너뛰므로, 원인만 고치면 **앞으로 올 예약**은 들어와도 반려된 건은 영영 빠진 채로 남는다.
  되살리려면 편집기에서 두 함수를 **순서대로** 실행한다:
  1. `reprocessMessages()` — 처리 기록을 비운다. **이것만으로는 아무것도 안 들어온다.**
  2. `processSpaceCloudReservations()` — 실제 재처리. 건너뛰면 다음 트리거까지 최대 15분 기다린다.

  기록을 통째로 비워도 **중복은 안 생긴다.** 등록은 `booking_no`가 이미 있으면 RPC를 부르기 전에
  빠져나가고(알림도 안 뜬다), 취소는 멱등이라 이미 취소된 건은 조용히 넘어간다. 그래서 재처리
  후 채널에 뜨는 "새 예약"은 **실제로 새로 들어온 것**뿐이다 — 그걸로 무엇이 복구됐는지 센다.
- 라벨은 이번 실행에서 건드린 스레드에만 붙인다. 포기한 메시지가 있으면 `spacecloud-error`,
  아니면 `spacecloud-processed`.
- 중복 등록 방지: `LockService`로 동시 실행(수동 실행과 15분 트리거가 겹치는 경우 등)을 막고, 예약번호가 이미 등록돼 있으면 등록을 건너뜀. DB에도 `booking_no` unique index가 있어 이중 안전장치.
- 처리 기록은 최근 300건만 남긴다(스크립트 속성 1개는 9KB 상한). 7일 창을 크게 웃도는 값이다.

## Mattermost 알림

예약 등록 / 취소 반영 / 처리 실패가 발생하면 Mattermost `e-alert-typelounge` 채널로 알림을 보낸다.

- 발송 경로: Mattermost **인커밍 웹훅**. URL은 커밋하지 않고 스크립트 속성 `MATTERMOST_WEBHOOK_URL`로만 주입한다.
- 반드시 공개 주소(`https://mm.nmwc.ai.kr/hooks/...`)를 쓴다. Apps Script는 구글 서버에서 실행되므로 `localhost:8065`에 도달할 수 없다.
- 알림 시점은 각 RPC가 **성공한 뒤**다. 중복 예약으로 등록을 건너뛴 경우엔 알리지 않는다.
- **알림 실패는 예약 처리에 영향을 주지 않는다.** `notifyMattermost`는 모든 예외를 삼키고 로그만 남긴다. 이렇게 하지 않으면 Mattermost가 잠시 죽었을 때 정상 등록된 예약까지 `spacecloud-error` 라벨이 붙어 재처리 대상에서 빠진다.
- 서버가 맥에서 cloudflared 터널로 노출되므로, 맥이 잠들어 있으면 알림만 유실되고 예약 데이터는 정상 반영된다.
- 알림 지연은 최대 15분(트리거 주기)이다.
- 요청사항처럼 자유 입력 값에 `|`나 개행이 들어와도 표가 깨지지 않도록 무해화한다.

## 운영 도구

Apps Script 편집기에서 함수를 골라 실행한다.

| 함수 | 용도 |
|---|---|
| `auditReservations(days)` | **진단 전용, 아무것도 바꾸지 않는다.** 메일과 DB를 대조해 누락·미반영을 실행 로그에 찍는다. 비우면 30일. 라벨 방식이던 시절 빠진 예약을 찾는 용도 |
| `dailyAudit()` | **일 1회 트리거로 자동 실행.** ① 신선도 — STALE_DAYS(3일) 이상 매칭 메일 0건이면 Mattermost 경보(백업 경로가 쿼리 수준에서 죽는 것을 잡는다). ② 대조 — auditReservations로 불일치를 훑어 있으면 요약 알림. 수동 실행도 가능 |
| `reprocessMessages()` | 처리 기록을 비워 창 안(7일) 메일을 재처리시킨다. 포기한 건을 원인 해결 후 되살릴 때 |
| `createTrigger()` | 트리거 설치 — 15분 `processSpaceCloudReservations` + 하루 1회 `dailyAudit`. 두 함수의 기존 트리거를 지우고 다시 만들어 **중복 설치되지 않는다** |

> `reprocessMessages()`는 등록을 예약번호로, 취소를 멱등성으로 거르므로 이미 반영된 건이
> 중복되지 않는다. 예약번호 추출 실패는 이제 조용히 null로 들어가지 않고 에러로 죽으므로,
> **null 예약번호로 인한 중복 등록은 이 수정 이전에 들어간 행에만 해당한다**(현재 DB엔 없을 것). 의심되면 먼저 `auditReservations()`로 확인한다.

## 범위 / 제약

- 스페이스클라우드(`스클`) 메일만 처리. 네이버 예약 메일은 다루지 않음(추가 필요 시 `GMAIL_QUERY`와 파싱 함수를 확장).
- 취소는 (날짜+시작+종료 시간) 일치로 찾되, 후보가 여럿이면 예약자명으로 특정한다 — A가 취소한 슬롯을 B가 재예약하면 취소·활성 두 행이 한 슬롯에 공존할 수 있어서다(동시 활성 2건은 단일 공간이라 여전히 없다).
- 인당/전화/이메일 등 이 메일에 없는 필드는 비워둠 → **주 경로(API)가 이 구멍을 메운다.**

## 막혔을 때

| 증상 | 원인 / 대응 |
|---|---|
| Mattermost에 "예약번호(booking_no)를 찾지 못했습니다" 실패 알림 | 스클이 예약 상세 링크 형식을 바꿔 `reservation%2F(\d+)`/`reservation/(\d+)` 정규식이 안 맞는 것. `parseReservationEmail`의 패턴을 실제 메일 원문에 맞춰 고친다. 예전엔 null로 조용히 들어갔지만 지금은 에러로 승격돼 알림이 온다 |

## 주 경로 — 파트너 API → Supabase

`spacecloud-api-sync.js`. 호스트센터 프론트가 쓰는 내부 REST API에서 예약을 직접 받아온다.

### 실행

1. 크롬에서 `https://partner.spacecloud.kr/reservation` 열기 (로그인 상태)
2. 개발자도구 콘솔에 `spacecloud-api-sync.js` 전체를 붙여넣기
3. 실행:
   ```js
   await scSync.run('<admin.html 비밀번호>', { dryRun: true })  // 미리보기, DB 변경 없음
   await scSync.run('<admin.html 비밀번호>')                    // 신규 예약 등록 + 취소 반영
   await scSync.fillContacts('<admin.html 비밀번호>')           // 기존 예약의 빈 연락처·이메일만 백필
   await scSync.fetchAll()                                      // 수집만 (비밀번호 불필요)
   ```

예약번호로 중복을 거르므로 **몇 번을 돌려도 안전하다.**

### 연락처 백필 (`fillContacts`)

`admin_fill_contact` RPC(`supabase/migrations/20260803020000_admin_fill_contact.sql`)를 쓰며,
**이미 값이 있는 칸은 절대 덮어쓰지 않는다** — 수동으로 고친 값이 API 값에 밀리지 않도록.

### 인증 — 24시간마다 재로그인이 필요하다

2026-08-03 실측으로 확인된 제약:

| 항목 | 결과 |
|---|---|
| 토큰 위치 | `localStorage["spacecloud__userInfo"].accessToken` |
| 헤더 | `Authorization: Bearer <token>` |
| 수명 | **정확히 24시간** (JWT 클레임은 `partner_id`·`exp` 뿐) |
| 리프레시 토큰 | **없음** |
| 인증 쿠키 | **없음** (쿠키는 전부 GA·채널톡·Datadog) |
| `/partner/users/get_token`으로 자체 갱신 | **불가** (401 `Missing token` — 소셜 콜백 전용) |

즉 만료되면 **재로그인만이 유일한 길**이다. 두 경로가 있고 **둘 다 동작을 확인했다**:

- **A. 네이버 OAuth (권장)** — 로그인 페이지에서 "네이버로 호스트 로그인" 클릭 한 번.
  비밀번호가 개입하지 않고, 네이버 세션만 살아 있으면 리다이렉트만으로 새 24시간 토큰이 발급된다.
  `scSync.ensureSession()`이 이 버튼을 눌러준다. 계정은 네이버 연동만 켜져 있다(카카오 OFF).
- **B. 이메일+비밀번호 (폴백)** — 크롬 자동입력이 채워둔 폼을 제출. 2026-08-03 통과 확인.
  단 Cloudflare Turnstile(invisible 모드)이 걸려 있고, 자동입력은 그 크롬 프로필에만 있으므로
  **다른 프로필·헤드리스 환경으로는 이식되지 않는다.** A가 막혔을 때만 쓴다.

네이버 세션 자체가 끊기면 그때만 사람이 네이버에 로그인하면 된다.

> **2026-08-04 정정 — 세션은 하루 만에 끊겼다. 무인 갱신은 불가능하다.**
> 사람 없이 토큰을 얻을 수 있는지 확인하려고 토큰을 지우고 네이버 OAuth를 태웠더니
> `nid.naver.com/nidlogin.login`(로그인 폼)에서 멈춰 6초가 지나도 움직이지 않았다.
> **네이버 세션이 없으면 리다이렉트만으로 통과하지 않는다** — 사람이 아이디·비밀번호를 넣어야 한다.
> 위의 "몇 달에 한 번"은 실측이 아니라 추정이었다. 8/3 로그인 바로 다음 날 세션이 없었으니
> A 경로가 그날 실제로 쓰인 게 맞는지도 확실하지 않다(폴백 B였을 가능성).
>
> 같은 실험에서 재확인된 것 — 인증 쿠키는 여전히 **0개**(GA·채널톡·Datadog뿐)이고,
> 토큰을 지우면 앱이 `{}`만 써놓고 로그인 페이지로 보낸다(자동 갱신 경로 없음).
>
> **그래서 연락처 백필은 완전 무인화가 안 된다. 토큰 갱신만 사람이 하는 반자동이 상한이다.**
> 세션 수명은 아직 열린 질문이다 — 네이버에 "로그인 상태 유지"를 켜고 로그인한 뒤 며칠 지나
> `contact-backfill/`의 `npm run spike`를 다시 돌리면 답이 나온다. 그 전에 무인 경로를 짜는 건
> 두 번째 추측이다.

### 엔드포인트

베이스: `https://api.spacecloud.kr`

| 용도 | 엔드포인트 |
|---|---|
| 예약 목록 (페이지네이션) | `GET /partner/reservations?page=N` |
| 예약 상세 | `GET /partner/reservations/:id` |
| 예약 승인 / 취소 | `POST .../approve`, `.../cancel` |
| 변경요청 승인 / 거절 | `.../reservation_change_requests/:changeId/{approve,reject}` |
| 공간·상품·가격 | `/partner/spaces/*`, `/partner/products/*` |
| 문의·리뷰 답글 | `/partner/questions/*`, `/partner/reviews/:id/comments` |
| 운영 리포트 | `/partner/operation_reports` |

**연락처·이메일·인원·요청사항은 목록에 없고 상세에만 있다** — 그래서 건별로 상세를 한 번 더 부른다.

상태 코드: `RSCMP` 예약확정 · `USEDC` 이용완료 · `RCCMP` 취소완료 / `PAYCP` 결제완료 · `REFND` 환불

### ⚠️ `end_hour`는 포함(inclusive)이다

API가 `start_hour:"16", end_hour:"18"`이면 **실제 이용은 16시~19시 3시간**이다.
호스트 페이지에도 "16~19 시, 3 시간"으로 표시된다. 그래서 `p_end`는 반드시 `end_hour + 1`.

2026-08-03 예약 9건 전수 대조로 확인했다. 단가로도 교차 검증된다 —
`13-20 / 64,000원`은 inclusive 8시간 × 8,000원으로 정확히 떨어지지만
exclusive 7시간이면 9,142.86원이라는 단가가 나온다.

**이걸 놓치면 모든 예약이 1시간씩 짧게 들어간다.**

### 제약

- **비공식 API다.** 호스트센터 프론트(CRA SPA)가 쓰는 내부 엔드포인트로, 문서화된 공개 API가 아니다.
  예고 없이 스펙이 바뀔 수 있다 — 그래서 Gmail 백업 경로를 유지한다.
- **취소건은 개인정보가 마스킹된다.** `RCCMP` 상태면 예약자명이 `윤**`로 오고 연락처·이메일이 아예 없다.
  확정 시점에 미리 수집해두지 않으면 그 손님 연락처는 영구히 못 가져온다.
  스크립트는 이런 건을 `maskedAdds`로 따로 보고한다. 실명이 필요하면 Gmail 취소 메일을 보면 된다.
- **브라우저가 필요하다.** 토큰이 브라우저 localStorage에만 있어 서버 단독 실행이 불가능하다.
- `end_hour`가 23이면 `p_end`가 `24:00`이 된다. PostgreSQL `time` 타입은 이 값을 받지만,
  운영 시간상 실제로 발생한 적은 없다.

# 운영지표 수집

파트너 콘솔의 **통계** 화면(`partner.spacecloud.kr/report/statistics`)이 그리는 값을 그대로
`sc_daily_stats` / `sc_daily_keywords`에 쌓는다. 어드민 대시보드가 읽을 원장이다.

| 파일 | 역할 |
|---|---|
| `spacecloud-stats-sync.js` | 수집기 본체. 브라우저 콘솔에 붙여넣어도 되고, 아래 러너가 대신 넣어줘도 된다 |
| `run-stats-sync.mjs` | 한 줄 러너. 탭을 찾아 수집기를 주입하고 결과만 돌려준다 |

표는 셋이고 **역할이 다르다.**

| 표 | 무엇 | 누가 읽나 |
|---|---|---|
| `sc_daily_stats` | 우리가 **해석한** 33개 지표 (일별 1행) | 어드민 대시보드 |
| `sc_daily_keywords` | 일별 유입 키워드 TOP5 (비율) | 어드민 대시보드 |
| `sc_daily_raw` | API 응답 **원문** (지표 25필드 + 차트 12시리즈) | 사고 났을 때만 |

`sc_daily_stats`는 컬럼을 고르면서 **비율 전부와 `review_score_avg`, 그리고 스클이 앞으로
추가할 필드를 버린다.** 버리는 게 맞다(기간 비율은 일별 비율의 평균이 아니라 저장하면
오용된다) — 다만 **되찾을 방법이 없는 게 문제**라 원문을 따로 남긴다. 지금은 API가 지난
날짜를 계속 주니 다시 받으면 되지만, 그 보장이 영원하지 않고 리스팅이 내려가면 과거도 같이
사라진다. 파싱이 틀렸다는 걸 나중에 알아차렸을 때 대조할 자리다.

원문은 **해석하지 않는다.** 키 이름도 스클 것을 그대로 쓴다 — `show_data`가 사실은 클릭수라는
헷갈림까지 원문대로 남긴다(여기서 고쳐 쓰면 원문 보관의 유일한 쓸모가 사라진다).
읽을 때는 `admin_list_sc_raw(비밀번호, 시작일, 종료일)`.

## 돌리는 법

```bash
cd 06-applications/automation
node run-stats-sync.mjs --dry-run      # 미리보기 (자격증명 불필요, DB 변경 없음)
node run-stats-sync.mjs                # 최근 14일 재수집
node run-stats-sync.mjs --all          # 전체 기간 백필
```

자격증명은 `TL_STATS_KEY` 환경변수로 주거나, 없으면 화면에 안 보이게 물어본다.
`aside`(Aside 브라우저 CLI)가 깔려 있고 그 브라우저에 파트너 로그인이 살아 있어야 한다.

## 수집 자격증명 — stats 전용 키

적재 RPC(`admin_upsert_sc_daily`)는 **stats 전용 키**를 받는다(어드민 비밀번호도 받지만
아래 이유로 쓰지 않는다). 키가 하는 일은 지표 적재 하나뿐이라, 새도 피해가 지표 오염
(같은 날짜 재수집으로 복구)에 그친다.

**어드민 비밀번호를 쓰면 안 되는 이유**: 러너는 자격증명을 **partner.spacecloud.kr 페이지의
JS 컨텍스트**에 주입한다(그 페이지의 세션을 빌려야 해서 — 위 "화면을 긁지 않는 이유").
그 페이지는 우리가 통제하지 않으므로, 거기서 어드민 비밀번호가 새면 예약자 이름·연락처를
여는 `admin_*` RPC 전체가 열린다. 전환기 호환으로 `TL_ADMIN_PASSWORD`도 아직 받지만
받을 때마다 경고가 찍힌다 — 경고가 보이면 아래로 갈아탄다.

**발급·회전** (Supabase SQL 편집기 또는 psql):

```bash
openssl rand -hex 32                   # 키 생성 — 사람이 외울 값이 아니다
```

```sql
select public.stats_set_key('<어드민 비밀번호>', '<생성한 키>');
```

그다음 실행 환경의 `TL_STATS_KEY`를 새 값으로 바꾼다. 끝 — 회전도 같은 두 단계다.

> 이 키는 어드민 비밀번호 회전 세 자리(`control-setup.md` M절)와 **무관하다.** 어드민을
> 회전해도 이 키는 살고, 이 키를 회전해도 어드민은 안 움직인다 — 네 번째 자리가 아니다.
> 키를 잃어버려도 잠기지 않는다: 심기 전·분실 시엔 어드민 비밀번호로도 적재가 되므로
> (`stats_or_admin_check`), 그때 새 키를 심으면 된다.

토큰이 죽었으면 러너가 종료코드 `2`와 함께 로그인 안내를 낸다. 그때만 사람이
`partner.spacecloud.kr/auth/login`에서 네이버로 한 번 로그인하면 된다.

## 화면을 긁지 않는 이유

통계 화면의 그래프는 전부 `<canvas>`라 DOM에 숫자가 없다. 대신 그 화면이 부르는 API를 그대로 쓴다:

```
GET api.spacecloud.kr/partner/statistics?start_date&end_date&space_id&type
    -> Chart.js 형태 { labels:["07.22",...], datasets:[{label,data:[...]}] } 12종
GET api.spacecloud.kr/partner/host_stat_indicators?...
    -> 집계 스칼라 25종 + search_word_data(유입 키워드)
```

둘 다 `Authorization: Bearer <파트너 토큰>`만 받는다. 토큰은 예약 동기화와 같은 것을 쓴다.

## 왜 무인으로 안 도는가

토큰이 브라우저 localStorage에만 있고 24시간이면 죽는데, 갱신 수단이 네이버 OAuth뿐이라
**사람만 뚫는다**(`contact-backfill/README.md`의 2026-08-04 실측). 그래서 cron·launchd에
얹지 않는다 — 토큰이 죽은 날 조용히 실패하고, 지표는 D-1이라 그날 안에 아무도 눈치채지 못한다.

**대신 걸러도 안 빈다.** 매 실행이 최근 14일을 통째로 다시 받아 덮어쓰므로, 며칠 만에 돌려도
빠진 날이 저절로 메워진다. 그게 이 설계가 무인화 없이도 버티는 이유다.

## 이 데이터를 쓸 때 반드시 아는 것 넷

전수 대조(2026-08-15, 07-22~08-14 24일)로 확인한 함정이다. 대시보드를 짜기 전에 읽는다.

|---|---|
| **`re_reservation_count`를 SUM하면 틀린다** | 재예약 판정이 조회 구간에 의존한다. 일별 합 20 ≠ 기간 조회값 22. 기간 재예약수가 필요하면 API를 그 기간으로 다시 부른다 |
| **확정 수치가 두 벌이다** | 차트 `rsv_*`는 **총액**, 지표 `reservation_*`는 **순액**(취소분 제외). 기간 전체로는 1,345,800 − 360,000 = 985,800으로 맞지만, **일별로는 24일 중 4일이 어긋난다** — 확정일과 취소일이 다른 예약 때문. 즉 **일 단위 순매출은 계산할 수 없다** |
| **키워드 값은 건수가 아니라 비율(%)** | 게다가 상위 5개에서 잘려 하루 합이 73~101로 들쭉날쭉하다. 날짜를 합쳐 기간 상위를 구하면 틀린다 |
| **비율은 저장하지 않는다** | 기간 비율은 일별 비율의 평균이 아니다. `reservation_approve_count = 0`인데 `approve_rate = 100`인 날도 있어(즉시예약, 분모 0) 분모를 카운트로 복원할 수 없다. 화면에서 그때그때 계산하고 0 나눗셈을 막는다 |

그 밖에 **오늘(D-0)은 쓰지 않는다.** 오늘 날짜로 API를 부르면 에러가 아니라 **말끔한 0**이
돌아와서(2026-08-15 실측: `labels=[]`, 전 지표 0) 그대로 넣으면 '집계 전'과 '장사가 안 된 날'이
영영 구분되지 않는다. 수집기와 RPC가 각각 한 번씩 막고 있다.

## 막혔을 때

| 증상 | 원인 / 대응 |
|---|---|
| 러너가 종료코드 2 + 로그인 안내 | 파트너 토큰 만료(24시간). 네이버로 다시 로그인하면 끝 |
| `수집기 응답을 찾지 못했습니다` | `aside`가 없거나 브라우저가 안 떠 있다. `aside repl "console.log(1)"`로 먼저 확인 |
| `구간에 집계된 데이터가 없습니다` | 리스팅 시작(2026-07-22) 이전 구간을 요청했거나 정말 데이터가 없다 |
| 특정 날짜만 계속 비어 있다 | 차트 라벨은 **집계가 0인 날을 아예 빼고** 온다. 첫 라벨 이후의 결번은 수집기가 0으로 채우지만, 첫 라벨보다 앞선 날은 '없음'이라 쓰지 않는다 |
| RPC가 `오늘(D-0) 이후 날짜는 넣을 수 없습니다` | 정상 방어다. 기기 시계나 `--to` 인자를 확인한다 |
