# 지원금(페이백) 신청 접수

`payback.html`(`/payback`)과 어드민 **지원금 신청** 탭이 쓰는 Edge Function.
공간 지원 프로그램 참여자가 이용 비용을 청구하면 접수하고, 어드민이 지급·반려를 처리한다.

**이 함수는 이 레포에서 가장 민감한 값을 다룬다 — 주민등록번호와 계좌번호다.**

## 주민번호를 받아도 되는가 (근거는 동의가 아니다)

지원금은 사업소득으로 지급되어 **3.3%를 원천징수**한다. 원천징수한 세금을 신고하려면
**지급명세서**에 주민번호를 적어야 하고, 그건 소득세법상 의무다. 즉 수집 근거는 소득세법이지
정보주체의 동의가 아니다 — 「개인정보 보호법」 §24-2는 주민번호를 동의로 수집하는 것을
원칙적으로 금지한다.

그래서 `payback.html`의 주민번호 고지는 "동의해 주세요"가 아니라 **"법령에 따라 받습니다"**로
쓰여 있다. 다른 항목처럼 동의형으로 고치면 근거가 어긋난다.

## 암호화는 선택이 아니라 강행 규정이다

같은 조 ③항이 안전성 확보 조치(암호화 저장)를 의무로 둔다. 이 함수의 구조 전체가 거기서 나온다.

| 원칙 | 어디에 |
|---|---|
| 암호화는 **DB가 아니라 여기서** 한다 | `crypto.ts` — pgcrypto를 쓰면 키가 SQL에 실려 쿼리 로그에 남는다 |
| 키는 **Edge Function 시크릿에만** 있다 | `RRN_ENCRYPTION_KEY` — DB에는 복호화 수단이 없다 |
| 키가 없으면 **접수를 거부**한다 | 평문 폴백이 없다. 시크릿을 빠뜨린 배포가 평문 저장으로 이어지면 안 된다 |
| IV는 **값마다 새로** | 재사용하면 키 없이도 '두 사람의 주민번호가 같다'가 드러난다 |
| 목록은 **마스킹 값만** 읽는다 | 화면 그릴 때마다 복호화하면 볼 필요 없는 순간에도 평문이 생긴다 |
| 복호화는 **한 건씩, 어드민만** | `reveal` action |
| 알림에는 **넣지 않는다** | `notify.ts` — 채널 글은 검색되고 전달되고 우리 파기 시점과 무관하게 남는다 |

**DB가 통째로 새도 주민번호는 안 새는 것**이 이 설계의 목적이다.

## action

| action | 누구 | 하는 일 |
|---|---|---|
| `submit` | 공개 | 검증 → 암호화 → 저장 → 알림. 비밀번호 없음 |
| `reveal` | admin | 한 건의 주민번호·계좌를 복호화해 돌려준다 |
| `mark_paid` | admin | 지급 완료 표시. **파기 시점이 여기 매달려 있다** |
| `reject` | admin | 반려 + **암호문 즉시 파기** |

`apply`와 합치지 않은 이유: 저기는 공개 액션 하나뿐이라 인증이라는 개념이 없다. 거기에
어드민 전용 복호화를 얹으면 실수 하나가 공개 경로에서 주민번호를 여는 사고가 된다.

## 리뷰는 확인만 받고 캡처는 받지 않는다

지원금은 리뷰를 남긴 사람에게 준다. 그 확인을 **체크박스 하나**로 받고(`reviewDone`),
서버가 `=== true`인지 자른다 — 동의와 같은 이유다(체크박스는 `fetch`로 그냥 빠진다).
접수되면 `review_confirmed_at`에 **접수 시각**이 찍힌다(boolean이 아닌 이유는 마이그레이션 주석).

**캡처 이미지는 받지 않기로 했다(형운, 2026-08-10).** 이미지를 받으면 Storage 버킷 · 업로드
경로 · 서명 URL이 생기고, 무엇보다 **파기 대상이 하나 더** 늘어난다 — 주민번호와 같은
생애주기로 지워야 하는데 SQL 크론은 Storage를 못 지운다. 신청자의 확인만 받고 실제 리뷰는
사람이 판매 채널에서 대조하는 쪽이 가볍고 정확하다.

그래서 화면과 알림 모두 **'확인됨'이 아니라 '남겼다고 함'**으로 적는다. 둘을 같은 말로 쓰면
대조를 건너뛰게 된다.

## 검증에서 하지 않는 것 (일부러)

**주민번호 체크섬을 검사하지 않는다.** 2020-10-06 이후 발급분은 뒷자리 6개가 임의 부여로
바뀌어 옛 검증식이 성립하지 않는다. 체크섬을 넣으면 **정상 발급된 최근 번호를 우리가 거절**하게
되고, 신청자는 왜 막혔는지 알 길이 없다. 대신 자릿수·성별코드·생년월일까지만 본다.

## 파기

| 상태 | 언제 | 무엇을 |
|---|---|---|
| 지급완료 | 지급 **1년 후** (크론) | 주민번호·계좌 암호문 |
| 반려 | **즉시** (반려 처리 시) | 주민번호·계좌 암호문 |
| 접수된 채 방치 | 접수 1년 후 (크론) | 주민번호·계좌 암호문 |

**행은 지우지 않는다** — 누구에게 얼마를 언제 지급했는지는 회계 기록이다. 파기 대상은 컬럼이다.

⚠️ **지급 후 '지급 완료'를 누르지 않으면 파기가 시작되지 않는다.** 크론이 매달 곳이
`paid_at`이라서다. 어드민 화면에 그 경고가 적혀 있다.

## 시크릿

| 이름 | 없으면 |
|---|---|
| `RRN_ENCRYPTION_KEY` | **접수 자체가 503으로 거부된다** (평문 폴백 없음) |
| `ADMIN_PASSWORD` | 어드민 action 전부 503 |
| `MATTERMOST_WEBHOOK_URL` | 접수는 되고 알림만 안 간다 |

키 만들기 — **32바이트(AES-256)여야 한다**:

```bash
openssl rand -base64 32
supabase secrets set RRN_ENCRYPTION_KEY='<위 출력>'
```

⚠️ **키를 잃으면 기존 암호문은 영원히 못 연다.** 회전하려면 옛 키로 전부 복호화해 새 키로
다시 넣는 마이그레이션이 필요하다 — 지금은 그런 경로가 없다.

## 배포

```bash
supabase secrets set RRN_ENCRYPTION_KEY='...'   # 이게 먼저다
supabase db push                                 # 테이블 + 파기 크론 + admin_list_paybacks
supabase functions deploy claim
deno test --allow-env supabase/functions/claim/  # 암복호화·검증 (키·DB 불필요)
```

**순서가 중요하다.** 키 없이 함수만 올리면 모든 접수가 503으로 튕긴다.

## 아직 검증 안 된 것

- **실기기 종단 확인.** 로컬에서는 순수 함수(암복호화·검증)와 화면 동작까지 확인했다.
  배포 후 실제로 한 건 넣어 `reveal`까지 밟아봐야 한다 — 다만 **테스트로 진짜 주민번호를
  넣지 않는다.** 형식만 맞는 가짜 번호로 확인하고 그 행은 지운다.
- **어드민 로그인이 필요한 경로 전체.** 평문 어드민 비밀번호가 없는 쪽에서는 확인할 수 없다.
- 지급명세서 제출 주기와 실제 보관 의무 기간은 **세무사 확인이 필요하다.** 지금 1년은
  형운 결정(2026-08-10)이지 세법이 정한 값이 아니다.
