## 결정 기록

### 길이 초과를 자르지 않고 거절한다 (2026-08-10)
- **결정:** 상한(`purpose` 1000자 등)을 넘으면 잘라 저장하지 않고 400으로 거절한다.
- **대안:** 상한까지 잘라 저장하고 접수는 성공 처리.
- **사유:** 조용히 자르면 신청자는 다 보냈다고 믿는데 우리는 잘린 것을 읽고, 잘렸다는 사실이 아무 데도 안 남는다.
  1000자는 DB 위생이 아니라 **Mattermost 4000자 본문 상한을 지키는 실질적 장치**이기도 하다 —
  여기를 열어두면 긴 신청 하나가 알림 단계에서 거절당해 알림만 조용히 사라진다.

### 스팸 덫에 걸린 요청을 성공으로 위장한다 (2026-08-10)
- **결정:** 화면 밖 `website` 칸이 채워져 오면 저장·알림 없이 200 `{ok:true}`로 답한다. 덫 판정은 다른 모든 검증보다 앞이다.
- **대안:** 400으로 거절하고 스팸이라고 알린다.
- **사유:** 400을 주면 보낸 쪽이 덫의 존재를 알아채고 다음엔 그 칸을 피해 간다. 덫보다 먼저 다른 검증을
  돌려도 같은 문제다 — 봇이 엉망으로 채운 요청에 400을 주는 순간 "무언가 걸렀다"는 신호가 된다.

### 저장 실패는 500, 알림 실패는 200 (2026-08-10)
- **결정:** 순서를 검증 → 저장 → 알림으로 고정하고, 저장 실패만 신청자에게 실패로 답한다.
  알림·`notified_at` 표시 실패는 로그만 남기고 접수는 성공으로 처리한다.
- **대안:** 알림까지 성공해야 접수 성공으로 답한다 / 알림을 먼저 보내고 저장한다.
- **사유:** 신청자는 이미 다 적어서 보냈고 우리 채널 사정은 그 사람 책임이 아니다. 순서를 뒤집으면
  웹훅이 죽어 있던 동안의 신청이 통째로 사라진다. 못 간 알림은 `notified_at` null로 드러나고
  어드민 탭이 '알림 못 감' 배지로 보여준다 — 재시도 큐를 두지 않은 이유도 이것이다(하루 몇 건짜리 단발).

### 탈락 상태를 만들지 않았다 (2026-08-10)
- **결정:** 상태를 `received`·`selected`·`held` 셋으로 두고 '탈락'을 넣지 않는다.
- **대안:** `rejected` 상태와 탈락 안내 문구를 함께 만든다.
- **사유:** 보류 문구가 "자리가 생기면 연락드린다"라 사실상 대기열이다. 명시적 탈락을 만들면 그에 맞는
  문구가 하나 더 필요하고, 그 문구는 되돌릴 수 없는 통보가 된다. 필요해지면 CHECK에 `rejected`를 더한다.

### 중복 발송 방어를 (application_id, kind) 부분 유니크로 (2026-08-10)
- **결정:** `application_sms`에 `(application_id, kind)` 유니크 인덱스를 걸되 `failed`·`superseded`는 제외한다.
  발송 전에 행을 먼저 insert(선점)하고, 유니크 위반(23505)이면 `already`로 돌려준다.
- **대안:** 보내기 전에 SELECT로 '이미 보냈나' 확인 / `(application_id)` 단독 유니크.
- **사유:** SELECT 확인은 두 호출이 나란히 통과해 같은 문자가 두 번 나간다 — 받는 사람은 두 번 선정된 줄 안다.
  키에 `kind`가 없으면 보류 문자를 받은 사람이 나중에 선정됐을 때 선정 문자가 막힌다(그 경로가 정상이다).
  `failed`·`superseded`가 자리를 비워야 재시도와 수동 발송 기록이 들어온다.

### 결과 문자는 preview → 발송 2단계 (2026-08-10)
- **결정:** [선정]/[보류]를 눌러도 바로 나가지 않는다. 서버 `preview`가 만든 실제 문구를 모달에 띄우고,
  거기서 [이 문자로 보내기]를 눌러야 발송된다. 문구는 항상 서버(`templates.ts`)가 만들고 호출측이 본문을 넘기지 못한다.
- **대안:** 어드민이 문구를 조립해 보여주고 그대로 발송 / 확인 없이 즉시 발송.
- **사유:** 문자는 되돌릴 수 없고 받는 사람에게는 그게 통보다. 문구를 만드는 곳이 서버 한 곳이라는 점이
  "미리 본 문장 = 나간 문장"의 유일한 보장이다 — 어드민이 조립하면 확인 절차는 승인 장치가 아니라 장식이 된다.

### 상태를 먼저 저장하고 문자를 보낸다 (2026-08-10)
- **결정:** `decide`는 `status`·`decided_at`·`admin_memo`를 먼저 update한 뒤 발송한다.
- **대안:** 발송에 성공했을 때만 상태를 바꾼다.
- **사유:** 뒤집으면 문자는 갔는데 상태가 안 바뀐 건이 남고, 다음에 또 보내게 된다. 반대 방향의 실패
  (상태는 바뀌고 문자는 못 감)는 장부와 어드민 화면에 드러나므로 둘 중에는 이쪽이 훨씬 낫다.

### 수동 발송은 기존 행을 고치지 않고 새 행을 만든다 (2026-08-10)
- **결정:** `mark_manual`은 `failed`·`superseded`가 아닌 기존 행만 `superseded`로 내리고, `manual` 행을 새로 insert한다.
- **대안:** 실패한 행의 status를 `manual`로 update.
- **사유:** 고쳐 쓰면 장부가 '실패했는데 성공으로 적힌' 거짓말을 하게 된다. 무엇이 실패했고 그래서
  사람이 무엇을 했는지가 둘 다 남아야 한다(`reservation_sms`와 같은 규칙). `failed` 행을 일부러 건드리지 않는 것도 같은 이유다 —
  유니크 인덱스에서 이미 빠져 자리를 막지 않는다. 대가는 화면이다: 그 건은 직접 발송을 기록한 뒤에도
  '발송 실패' 줄과 [문구 복사 · 직접 발송] 버튼이 함께 남는다.

### 목록 조회 실패를 빈 목록으로 두지 않는다 (2026-08-10)
- **결정:** `admin_list_applications`가 실패하면 목록을 비우고 경고 문구를 띄운다. 문자 이력 조회 실패는
  목록 렌더를 막지 않는다.
- **대안:** 실패 시 빈 목록('아직 신청이 없어요') 표시 / 둘 중 하나라도 실패하면 화면 전체를 막는다.
- **사유:** '신청 없음'으로 오해하면 읽는 사람은 그냥 닫고, 조용히 사라진 신청은 없는 기능보다 나쁘다.
  반대로 이력을 못 받았다고 목록까지 안 보이면 결과를 정하는 일 자체가 막힌다.

### 어드민 조회는 RPC, 결정은 Edge Function (2026-08-10)
- **결정:** 읽기는 SECURITY DEFINER RPC(`admin_list_applications`, `returns setof support_applications`),
  쓰기·발송은 `functions/apply`의 어드민 action으로 나눈다. RPC의 비밀번호 검증은 `admin_list_reservations`에 위임한다.
- **대안:** 조회도 Edge Function으로 통일 / RPC마다 비밀번호를 다시 박는다.
- **사유:** `setof`로 두면 나중에 컬럼이 붙어도 자동으로 실려 나간다(실제로 `status`·`decided_at`·`admin_memo`가
  붙었을 때 이 함수를 안 고쳤다). 평문 비밀번호를 SQL에 또 박으면 같은 비밀이 늘어나기만 하고 바꿀 때 한 군데를 빠뜨린다.
  ⚠️ 대가: RPC 경로는 Edge Function의 시도 제한 밖이다(`spec_admin_auth` Future Work).
