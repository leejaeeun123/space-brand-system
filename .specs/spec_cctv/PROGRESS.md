### 현장 감시자가 막혀 있는 이유 (2026-08-18 실측)

**launchd가 띄운 Node는 카메라 LAN에 못 붙는다.** 같은 바이너리·같은 스크립트인데
터미널에서는 되고 launchd에서는 안 된다:

| 실행 경로 | 결과 |
|---|---|
| 터미널 + Node | `HTTP 200` 도달 |
| launchd + Node (`/usr/local/bin/node`) | `EHOSTUNREACH connect 192.168.200.193:2020` |
| launchd + `curl` (Apple 서명) | `HTTP 200` 도달 |

§16-3의 ffmpeg와 **같은 벽**이다(macOS 26이 로컬 네트워크 접근을 바이너리 단위로 통제).
`curl`이 되는 것은 Apple 서명 도구라 그렇고, `nc`가 되는 것과 같은 이유다 — 우리 문제를
풀어주지 않는다.

`control-agent`는 바로 그 launchd 아래에서 `/usr/local/bin/node`로 돈다. 그래서
**감시자를 에이전트 안에 넣으면 조용히 아무것도 못 본다** — 에러도 안 나는, 제일 나쁜 실패다.

**해결: 감시자를 `camera-relay-all.sh`에 얹었다**(형운 결정, 2026-08-18).
`TypeLoungeCameraRelay.app`(ad-hoc 서명 + `NSLocalNetworkUsageDescription` + 네이티브 런처)이
이미 LAN 권한 주체로 통과한 상태라, 그 자식으로 띄우면 권한을 물려받는다. 검토했다 버린 대안 둘:

- **감시자 전용 `.app` 신설** — 책임은 깨끗하지만 권한 승인을 한 번 더 밟아야 한다.
  새 번들에 로컬 네트워크 권한을 처음 줄 때 **사람이 현장 맥에서 승인해야 할 수 있는데**,
  무인 운영이라 그 클릭을 누를 사람이 없다.
- **`control-agent` 자체를 `.app`으로 이전** — 조명·냉난방까지 같이 걸려 가장 위험하다.

> 재발행과 감시가 한 지붕에 있는 것이 어색해 보이지만, **둘의 공통점이 정확히 그 권한 경계**다 —
> "카메라 LAN에 말을 거는 것"이 이 `.app`의 책임이다.

### 같은 벽에 걸려 있을 수 있는 것 — 조명 HTTP 우회

`tasmota-http.js`의 `pollHttpState`도 `192.168.200.x`로 붙는다. **launchd 직속인
`control-agent`에서 도는 코드라 같은 이유로 못 붙을 가능성이 크다.** 브릿지가 살아 있으면
아예 안 도는 경로라 아직 실제로 밟힌 적이 없어 확인되지 않았다 — 조명이 '먹통인데 이유를
모르겠다'가 되면 여기부터 의심한다. [확인 필요]

### ONVIF에서 실측된 제약 (2026-08-18)

| 사실 | 근거 |
|---|---|
| `PullMessages`의 `Timeout`은 **`PT9S` 이하**여야 한다 | `PT10S` 이상이면 응답 없이 11초에 연결이 끊긴다. `PT1S`~`PT9S`는 전부 0.0초에 200 |
| 카메라가 **롱폴링을 하지 않는다** | 어떤 `Timeout`을 줘도 큐에 있는 것만 즉시 돌려준다 → 감지 지연의 상한은 우리 폴링 간격이다 |
| **WS-Security가 필수** | 없으면 `Authority failure`. WS-Addressing(`To`·`Action`)은 있어도 없어도 된다 |
| 구독은 2대 동시 15분 유지된다 | `Renew`(`PT10M`)를 4분마다 선제 발행. 만료를 기다렸다 실패로 재구독하면 10분마다 실패 버스트가 난다 |
| 사람 감지는 **켜져 있지 않다** | 토픽은 `PeopleDetector/People`까지 광고하지만, 가동 중인 분석 모듈은 `CellMotionEngine`·`TamperEngine` 둘뿐 |
| **사이렌은 ONVIF로 못 울린다** | `GetRelayOutputs`·`GetAudioOutputs` 모두 `ter:ActionNotSupported`. Tapo 제어 API(`startManualAlarm`)뿐이고 클라우드 비번이 필요하다 |

## 결정 기록

### 퇴실 독려는 이벤트 경로를 ONVIF로 간다 (2026-08-18)
- **결정:** 움직임 감지를 Tapo 제어 API가 아니라 **ONVIF PullPoint**로 받는다.
- **대안:** pytapo `getEvents` — Tapo 클라우드 비번 + `admin` 계정.
- **사유:** 카메라 계정으로는 제어 API가 아예 안 열린다(실측). ONVIF는 **이미 `.env`에 있는
  `CAM_RTSP_USER`/`CAM_RTSP_PASS`로 열리고**, 새 비밀을 현장 맥에 더 두지 않아도 된다.
  덤으로 SD카드에 의존하지 않는다 — `getEvents`는 SD 타임라인 조회라 SD가 없거나 순환에
  덮이면 조용히 빈 배열이 된다. 대가는 ONVIF가 **과거를 못 묻는다는 것**이라, 감시자가
  창이 열리기 전부터 계속 구독하고 있어야 한다.

### 움직임 이력을 쌓지 않는다 (2026-08-18)
- **결정:** `camera_motion`은 카메라 1대당 1행. 마지막 움직임 시각만 덮어쓴다.
- **대안:** 감지 1건마다 행을 남겨 이력 테이블로 둔다.
- **사유:** 판정에 필요한 것이 "창 안에 움직임이 있었나" 하나뿐이라 마지막 시각이면 답이 나온다.
  이력을 쌓으면 **사람이 공간에 있었던 시간대가 통째로 DB에 남는데**, 우리가 쓰지도 않을
  개인정보를 보관하는 것이고 §25의 태도와도 맞지 않는다. 영상·스냅샷은 애초에 올라오지 않는다.

### 퇴실 후에도 사람에게는 아무것도 하지 않는다 — 알리기만 (2026-08-18)
- **결정:** 운영자 Mattermost 알림만. 창당 **1회**. 손님 자동 문자·카메라 사이렌은 만들지 않는다.
- **대안:** 손님에게 SOLAPI 문자 / 카메라 사이렌·조명 경고.
- **사유:** 사람에게 할 수 있는 안전한 자동 조치가 없다(형운 결정, 2026-08-17). 문자는 §25 고지
  개정이 선행돼야 하고, 사이렌은 애초에 ONVIF로 못 울린다(`ter:ActionNotSupported`) — Tapo
  제어 API가 필요하다. 그리고 감지가 사람이 아니라 **셀 단위 움직임**이라, 오탐 한 번의 대가가
  채팅 한 줄과 빈 방의 사이렌은 전혀 다르다.

### 영상을 Supabase로 중계하지 않는다 (2026-08-03)
- **결정:** 브라우저가 합정 맥의 MediaMTX에 직접 붙는다. Edge Function은 주소·자격증명 전달과
  생존 확인만 한다.
- **대안:** 제어(`devices`)와 같은 경로로 영상도 서버를 지나게 한다.
- **사유:** 제어는 초당 JSON 한 건이지만 영상은 초당 수 Mbps다. Edge Function·DB로는 기술적으로도
  비용상으로도 못 나른다. 이 결정이 나머지 설계 전부(자격증명 전달·재연결·상태 감시 분리)의 전제다.

### 인증은 MediaMTX 내장(`authInternalUsers`)에 맡긴다 (2026-08-03)
- **결정:** 검증은 MediaMTX가 하고, 우리 서버는 그 계정을 admin에게 **전달만** 한다.
- **대안:** `authMethod: http` — 요청마다 Edge Function이 인증 서버가 된다.
- **사유:** HLS는 플레이리스트·세그먼트 **매 요청마다** 인증한다(초당 4~5회). 왕복이 끼면 재생이
  덜컥거리고, 시청 1시간당 약 1.6만 호출이라 하루 한 시간씩만 봐도 월 48만으로 무료 한도(50만)에
  닿는다. 대가인 '장기 유효 자격증명'은 세 가지로 상쇄했다 — 계정에 `publish`가 없고(가짜 영상
  덮어쓰기 불가), 받으려면 이미 admin 비밀번호를 통과해야 하고, 회수는 두 곳 동시 교체다.

### 자격증명은 Authorization 헤더로만 (2026-08-03)
- **결정:** `Basic` 헤더. hls.js `xhrSetup`이 요청마다 붙인다. 목록 응답에는 담지 않고 별도 action으로
  로그인 세션당 1회만 내려준다.
- **대안:** 쿼리스트링(`?user=&pass=`) 또는 목록 응답에 함께 싣기.
- **사유:** MediaMTX가 v1.18.0에서 쿼리스트링 자격증명을 보안 결함으로 규정해 막았고,
  `authMethod: internal`은 애초에 토큰을 보지 않는다. 헤더는 부수 이득도 있다 — 비밀이 URL에 안
  실려 cloudflared·MediaMTX 접근 로그에 찍히지 않는다. 목록은 15초마다 다시 받으므로 거기에 실으면
  비밀이 필요 이상으로 자주 돌아다닌다.

### 카메라를 `devices` 테이블에 넣지 않는다 (2026-08-03)
- **결정:** `cameras`·`camera_state`를 별도 테이블로 둔다.
- **대안:** `kind='camera'`로 기존 기기 테이블에 통합.
- **사유:** 카메라는 명령을 받지 않고 `power`가 없다. 통합하면 `capabilities=[]`·`power=null` 행이
  생기고, '상태 모름'을 경고로 표시하는 기존 UI가 카메라마다 영구히 경고를 띄운다. 형태가 같다고
  의미가 같은 게 아니다 — `devices`는 '제어할 수 있는 것', `cameras`는 '볼 수 있는 것'이다.

### 오디오는 ffmpeg `-an` 재발행으로만 뗀다 (2026-08-10)
- **결정:** `paths`를 전부 `source: publisher`로 두고 `rtspAddress`를 `127.0.0.1`에 묶어,
  로컬 ffmpeg 재발행을 MediaMTX로 들어가는 **유일 경로**로 만든다.
- **대안:** 카메라 앱에서 마이크 끄기 / MediaMTX 설정으로 오디오 트랙 버리기.
- **사유:** 카메라 3대 모두 앱에서 마이크를 껐는데도 RTSP에 `pcm_alaw`가 실려 나오는 것이 실측됐고,
  **MediaMTX에는 트랙을 버리는 설정이 없다.** 오디오가 서버로 흐르면 「개인정보 보호법」 §25⑤
  위반이다. 설정으로 못 막으므로 구조로 막고, 그래도 새는 경우를 대비해 오디오 트랙을 상태로
  승격해 감시한다(모르는 코덱은 오디오로 판정 — 오경보 쪽으로 틀리게 설계했다).

### 재발행을 네이티브 `.app` 번들로 띄운다 (2026-08-10)
- **결정:** `relay-launcher.c`를 컴파일해 `.app`의 실행 파일로 두고, launchd가 그것을 띄운다.
- **대안:** LaunchAgent에서 셸 스크립트 직접 실행 / 셸 스크립트를 실행 파일로 둔 `.app` /
  `osascript`로 Terminal 시키기.
- **사유:** macOS 26은 로컬 네트워크 접근을 **바이너리 단위**로 통제한다(TCC). launchd가 띄운
  Homebrew ffmpeg는 카메라 IP에 `No route to host`가 나고, 시스템 설정의 '로컬 네트워크' 목록에
  항목조차 안 떠서 토글로 풀 수도 없다. 셸 스크립트를 실행 파일로 두면 프로세스가 `/bin/bash`로
  잡혀 번들이 권한 주체로 인식되지 않는다. 시도 6가지 중 네이티브 바이너리만 통과했다.

### 서버 녹화를 끈다 (2026-08-10, 현장 지시)
- **결정:** `record: no` · `playback: no`. 합정 맥은 영상을 저장하지 않고, 되감기 UI도 걷어낸다.
  영상은 카메라 SD카드에만 남는다.
- **대안:** 고화질 7일 서버 녹화 유지(하루 20~40GB/대).
- **사유:** 현장 지시. 따라오는 결과 셋을 같이 처리했다 — (1) `recordDeleteAfter`가 파기 집행
  주체에서 내려와 보관기간 4곳 동기화가 휴면이 됐고, (2) 카드의 `녹화 중/안 됨`·`남은 용량`이
  고정값이 돼 장애 신호로 못 쓰게 되어 상태줄에서 뺐고(그 자리를 신호로 쓰던 습관이 진짜 경고를
  가린다), (3) 손님 고지의 '7일 자동 파기'가 집행 주체를 잃었다.
- **⚠️ 되켤 때:** `record`·`playback`을 함께 켜고 `recordDeleteAfter`를 4곳(게스트 가이드 · 현장
  안내판 · `mediamtx.yml` · `CAMERA_RETENTION_DAYS`)과 같은 숫자로 맞춘다.

### SD카드 실보관 일수는 감사 범위 밖 (2026-08-13, 오너 결정)
- **결정:** 감사 경계는 **'우리 서버'**다. 서버가 아무것도 저장하지 않으므로 파기할 것도 없고,
  카메라 SD카드의 실제 보관 일수는 추적·집행 대상이 아니다.
- **대안:** SD 순환 주기를 실측해 관리 대상에 포함.
- **사유:** 서버 녹화를 끈 뒤 "그럼 7일 파기는 누가 집행하나"가 남았는데, 경계를 서버로 그으면
  집행할 대상 자체가 없다. 다만 **손님 고지와 어긋날 수 있다는 사실은 별개로 남는다** — 문구는
  여전히 "7일 자동 파기"라고 말하고 있다.

### HLS 세그먼트를 1초 → 4초로 (2026-08-10)
- **결정:** `hlsSegmentDuration: 4s`. `hlsSegmentCount: 7`은 그대로 둔다(라이브 윈도우 7초 → 28초).
- **대안:** 세그먼트 수를 줄이기 / Tailscale 전환 / Cloudflare 유료 플랜.
- **사유:** Cloudflare Free가 서울 트래픽을 LAX 엣지로 보내 왕복이 0.73~0.94초다(플랜의 성질이라
  설정으로 못 고친다). 세그먼트를 4배로 늘리면 요청 수가 1/4이 되고, 윈도우가 넓어져 지터에도
  강해진다. 대가는 지연 몇 초뿐인데 "지금 저기 사람 있나"에는 문제가 안 된다. 세그먼트 수를
  줄이는 쪽은 반대 방향이다 — 윈도우가 좁아져 지터 한 번에 끊긴다.

### iPhone 400은 코드가 아니라 Transform Rule로 푼다 (2026-08-10)
- **결정:** Cloudflare Request Header Transform Rule로 `cam.nmwc.ai.kr` 요청의 User-Agent를
  `TypeLounge-Viewer/1.0`으로 덮어쓴다.
- **대안:** 어드민에 `?cookieCheck=1` 붙이기(실제로 한 번 넣었다가 걷어냄) / `withCredentials` 켜기 /
  Cloudflare Workers.
- **사유:** MediaMTX가 **iOS UA에만** 쿠키를 요구하는데(`isIOS` 분기 → 400), 교차 사이트라 브라우저가
  그 쿠키를 보낼 방법이 없다 — hls.js는 `withCredentials=false`가 기본이고, 켜도 MediaMTX가
  `Access-Control-Allow-Credentials`를 어떤 경로에서도 안 보낸다. 검사 자체가 성립하지 않게 만드는
  것이 유일한 길이었다. Workers는 무료 한도(10만/일)가 세그먼트 요청량에 아슬아슬한데 Transform
  Rule에는 요청 한도가 없다. `?cookieCheck=1` 우회는 **Set-Cookie를 받을 기회마저 없애서 오히려
  나빴다** — 오진 기록을 `admin.html` 주석에 남겼다.

### 재연결은 '안 끊기게'가 아니라 '돌아오게'를 목표로 한다 (2026-08-10)
- **결정:** 오류 종류별로 싼 수단부터 시도하고, 셋 다 같은 백오프 회계(1s→30s, 6회)를 태운다.
  소진하면 인스턴스를 정리하고 부착 표시를 지워 **15초 목록 갱신이 느린 재시도** 역할을 하게 한다.
- **대안:** 오류 문구만 칠하고 사람이 새로고침하게 두기(이전 동작) / 무한 재시도.
- **사유:** 태평양 왕복 환경에서 끊김은 없앨 수 없다. 이전 동작은 `CAM.attached`가 true로 남아
  **순간 끊김 하나가 새로고침 전까지 검은 화면으로 굳었고**, 그게 "자꾸 끊긴다"의 정체였다.
  무한 재시도는 이미 버거운 업링크를 1초마다 두드린다. 백오프 리셋을 30초 연속 재생 뒤로 미룬 것도
  같은 이유다 — 조각 하나로 리셋하면 플래핑에서 백오프가 1초에 고정된다.
- **검증:** `admin-retry.test.js`가 CI에서 돌고, 2026-08-10 터널 35초 다운으로 실기기 확인했다.

### 어드민 재연결 로직을 이름 있는 함수로 뽑는다 (2026-08-10)
- **결정:** `handleCamFatal`·`camMarkAlive`·`camRetry`를 핸들러 안 인라인이 아니라 이름 있는 함수로
  두고, 테스트가 `admin.html`에서 **본문을 이름으로 잘라내** 스텁 환경에서 돌린다.
- **대안:** 검증 없이 두기 / admin.html에 빌드 단계를 도입해 모듈로 분리.
- **사유:** 재연결이 틀렸을 때의 증상이 **조용하다** — 카드가 검은 화면으로 남을 뿐 오류가 어디에도
  안 뜨고, 알아차리는 시점은 대개 "그때 영상 좀 봅시다" 뒤다. 빌드 단계를 넣는 건 단일 HTML이라는
  이 파일의 성질을 바꾸는 큰 변경이라 미뤘다. 잘라내기가 실패하면 **즉시 죽는다** — 구조가 바뀌었는데
  테스트만 초록으로 남는 게 제일 나쁘다.

### 상태를 3분법으로 나눈다 (2026-08-03)
- **결정:** `never_seen`(보고 없음) · `is_stale`(180초 초과) · `online=false`(연결 끊김)를 각각 다른
  표시로 둔다. 에이전트는 관측 실패 시 **아무것도 쓰지 않는다.**
- **대안:** 전부 '오프라인'으로 합치기 / 관측 실패를 `online=false`로 쓰기.
- **사유:** 합치면 방금 등록한 카메라가 장애처럼 보이고, 반대로 진짜 장애가 왔을 때 아무도 그 경고를
  믿지 않게 된다. 관측 실패를 `false`로 쓰면 '카메라가 죽었다'와 '내가 못 봤다'가 구분되지 않는다 —
  안 쓰면 `updated_at`이 늙어 화면이 '보고 끊김'으로 표시하는데, 그게 실제로 일어난 일이다.
  `updated_at` 기본값을 `now()`로 주지 않는 것도 같은 규칙이다.
